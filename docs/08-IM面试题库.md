# 08 IM 面试题库

> 用法：每题给出「答题要点」，均以本项目实现为答案锚点（M0~M8 完成后补充代码位置引用）。
> 面试叙事总纲：先用 30 秒讲架构图（01 文档 §1），再按面试官追问展开对应模块。

---

## 一、整体架构

**Q1 介绍一下你的 IM 系统架构？为什么这样分层？**
- 五类服务：Gate（HTTP 接入）/ Status（注册中心+登录态）/ Chat（消息核心，持有长连接）/
  File（文件）/ AI（酒馆）；接入面与逻辑面分离（ADR-008）。
- 关键叙事：Gate 只做注册登录，消息面客户端直连 ChatServer——消息面少一跳，
  ChatServer 可独立水平扩容；Status 维护服务注册表与路由，是「大脑」但不承载数据面流量。

**Q2 服务间怎么通信？为什么不用 gRPC？**
- 自研 RPC：Protobuf + Asio 长连接 + 连接池 + requestId 匹配 + 超时重试（01 §4）；
- 理由：统一 boost 技术栈、可控可讲透；gRPC 引入框架掩盖细节；我们只需要最小集。
- 加分：能讲注册发现（心跳 30s×3 摘除）、负载均衡（最小连接数）、双向 Push（AI 流式依赖）。

**Q3 一条消息从发出到送达经历了什么？**
- 客户端 → ChatServer：幂等检查 → Redis INCR seq → MySQL 落库 → ACK → 投递
  （本机直推 / 查路由跨节点 RPC Push）→ 对端 ACK 已读（02 §4，01 §5.2）。
- 强调顺序：**先落库后投递**，ACK 语义是「服务端已持久化」。

**Q4 如何水平扩展？瓶颈在哪？**
- ChatServer 无状态可多开（路由表支撑）；Gate 前挂 Nginx；MySQL 分表演进（03 §5.3）；
- 瓶颈演进：单表消息量 → 分表；扇出写压力 → 大群读扩散；Status 单点 → 注册表 Redis 化后无状态化。

## 二、网络编程

**Q5 TCP 粘包/拆包怎么处理？**
- 12 字节定长帧头含 totalLength（02 §1）；接收侧 BufReader 状态机：凑头→解长→凑体；
- 面试陷阱：消息边界≠可靠序号——帧头 pktSeq 只做请求匹配，业务时序靠会话 seq。

**Q6 epoll 的 LT/ET 区别？你用的什么？**
- Asio 在 Linux 是 epoll，默认 LT 语义封装；我们依赖 Asio 异步模型（Proactor），
  Windows 下 IOCP，跨平台一致（本项目开发在 Windows，代码不直接触 epoll）；
- 能讲 ET 必须配非阻塞 + 循环读到 EAGAIN、LT 惊群差异即可。

**Q7 心跳为什么需要？怎么设计？**
- TCP keepalive 太慢且探测不到应用层假死；应用层心跳 30s/90s 判死（02 §5）；
- 心跳顺带刷新路由 TTL（route:uid），一举两得。

**Q8 断线重连怎么做才不引入重连风暴？**
- 指数退避 + 随机抖动（1s→60s，±20%）；重连后走 0x0105 免重登 + SyncRequest 补拉；
- 服务端侧：限流单 IP 连接建立速率。

**Q9 Reactor/Proactor 区别？**
- Reactor：就绪通知，应用自己读写（同步非阻塞）；Proactor：完成通知（Asio 模型）；
- 我们的应用层感知是「异步回调」，底层 Windows=IOCP/Linux=epoll。

**Q10 零拷贝了解吗？哪里能用？**
- sendfile（文件下载）、writev 聚合写；本项目 FileServer 下载路径可用；
- 应用层体现：BufReader 用 string_view 切片避免 memcpy（能讲实践即可）。

## 三、消息可靠性与一致性

**Q11 怎么做到消息不丢、不重、不乱序？**
- 不丢：先落库后投递 + 上线/重连按 lastSeq 游标补拉（推拉结合）；
- 不重：clientMsgId 幂等（Redis 去重 + MySQL 唯一键双保险）；
- 不乱序：会话级服务端单调 seq，客户端按 seq 渲染、空洞即补拉（02 §4 R1~R8）。

**Q12 为什么用会话级 seq 而不是全局 ID 或时间戳？**
- 会话级单调性才能判定「空洞」，全局 ID 无法；时间戳受时钟漂移影响且不连续；
- seq 由 Redis INCR 分配 + MySQL 唯一键兜底（03 §3.4）。

**Q13 在线消息和离线消息如何统一？**
- 统一为「拉」语义：在线推只是优化；本地最大连续 seq 是唯一游标，在线/离线/多端漫游同一套补拉协议。

**Q14 Redis 和 MySQL 的 seq 一致性怎么保证？**
- Redis 先行（性能），MySQL (conv_id, seq) 唯一键兜底（正确性）；冲突即 Redis 回档场景，
  以 MAX(seq)+1 重新分配并告警；Redis 开 AOF everysec（03 §3.4）。

**Q15 已读回执怎么设计？**
- last_read_seq 游标上报；未读数 = last_seq - last_read_seq 推导，不维护计数器，天然一致（03 §2.2）。

**Q16 撤回怎么实现？**
- 服务端校验 2 分钟窗口与发送者身份 → status=1 落库 → 双端通知；客户端渲染「撤回了一条消息」。

## 四、存储与缓存

**Q17 消息表怎么设计？为什么主键是 (conv_id, seq)？**
- 读写模式决定：按会话拉区间是最高频路径，聚簇顺序读；msg_id（雪花）另建索引寻址单条（03 §2.2）。

**Q18 读写扩散怎么选？**
- 单聊写扩散（每会话独立游标）；小群写扩散统一；大群读扩散（时间线）为演进项；
  判断标准：扇出比（消息数×成员数）与存储成本（ADR-006）。

**Q19 Redis 在你的项目里承担什么角色？**
- token、在线路由、seq 计数、幂等去重、群成员缓存、分布式锁、限流、nonce——
  全是「热、小、可丢（可重建）」的数据；权威数据一律 MySQL。

**Q20 分布式锁怎么实现的？锁超时了业务还没跑完怎么办？**
- SET NX PX + 唯一 value + Lua 释放（比对 value）；业务侧设看门狗续期或任务幂等可重跑
  （AI 摘要任务幂等：以 seq 游标为准，重跑无害）（04 §7）。

**Q21 缓存与数据库一致性？**
- 本项目缓存均为「可重建」型（成员表/路由），策略是变更时删除缓存 + 短 TTL 兜底；
  不引入复杂双写一致，讲清 trade-off 即可。

**Q22 雪花时钟回拨怎么办？**
- 序列号溢出等待 + 回拨小于阈值等待、大阈值报警拒绝服务；机器号配置分配。

## 五、性能

**Q23 你的压测怎么做的？数据如何？**
- 自研 simbot（复用客户端协议栈，一石二鸟）；基线 1000 连接×10msg/s，终版 3000 连接混合负载；
  P99 目标 ≤150ms、零丢失（07 §6）；瓶颈分析方法：慢查询 explain、火焰图、连接池命中率。

**Q24 服务端怎么扛住长连接？**
- 异步 IO + 每连接内存精简（缓冲区水位回收）+ 心跳判死清理 + 连接数上限；
- 仍能讲：C10K 本质是从「线程池+阻塞」到「事件驱动」的范式转变。

**Q25 连接池怎么设计？**
- MySQL/Redis 池：延迟初始化、健康检查（ping）、获取超时、归还检测、坏连接剔除；
- RPC 连接池同构（01 §4.1）。

**Q26 大群消息怎么优化？（演进题）**
- 写扩散扇出爆炸 → 读扩散时间线；在线成员合并推送（一帧多消息）；冷热分离。

## 六、安全

**Q27 登录态怎么设计的？**
- HMAC token（uid.expire.sig），无状态校验；ChatServer 经 Status RPC 校验；顶号：路由表冲突→踢旧（01 §5.1）。

**Q28 密码怎么存？**
- salt + SHA256（生产建议 bcrypt/argon2，预留接口）；传输走 HTTPS（公网）。

**Q29 防重放与越权？**
- HTTP：timestamp+nonce（5min 窗口 Redis 去重）；业务：一切会话操作校验 uid 归属（TC-SEC 矩阵）。

**Q30 消息内容安全？**
- 服务端 DFA 敏感词（热更新）；AI 输出双向过滤（04 §12）。

## 七、音视频

**Q31 WebRTC 通话建立流程？**
- Invite(带 Offer) → Ring → Accept(Answer) → ICE 候选交换 → DTLS 握手 → SRTP 媒体（05 §3）；
- 强调信令走 IM 长连接的复用价值。

**Q32 NAT 穿透原理？什么时候需要 TURN？**
- STUN 探测公网映射，双方同时发包开洞；对称型 NAT 之间打洞必败 → TURN 中转（05 §7 矩阵）；
- 我们给每路通话下发 10 分钟临时 TURN 凭证（HMAC），凭证不进客户端。

**Q33 音视频编解码选型？**
- Opus（语音 48k/自适应码率）+ H264 baseline（OpenH264 编码、FFmpeg 解码渲染）；
  选型理由：兼容性与 CPU 成本平衡（05 §5）。

**Q34 弱网怎么办？**
- RTCP 反馈（RTT/丢包）→ 码率降档；关键帧请求 PLI；音频优先保活（05 §6）。

## 八、AI / LLM 工程

**Q35 AI 角色怎么融入 IM 架构的？（项目亮点题）**
- AI 角色即用户（user_type=1），复用全部消息管线；AI 专属状态挂会话扩展表；
  ChatServer 按 user_type 分流到 AIServer（04 §1，ADR-011）。

**Q36 流式回复与消息可靠性冲突吗？**
- 不冲突：占位消息预占 seq（status=2），分片仅体验层，最终以 End 全文重写（02 R7，04 §6）。

**Q37 长上下文怎么管理？**
- 三级记忆：工作窗口 → 滚动摘要（seq 游标幂等）→ 事实卡；世界书按需注入省 token（04 §4/§7）。

**Q38 LLM API 不稳定怎么办？**
- 网关层：重试（幂等）、多 Provider 降级、令牌桶限流、超时兜底文案、ai:pending 队列崩溃恢复（04 §3）。

**Q39 Prompt 注入怎么防？**
- 用户输入分隔符包裹 + 声明非指令；平台输出契约不可被角色 prompt 覆盖（04 §12）。

## 九、客户端

**Q40 Qt 客户端线程模型？**
- UI 主线程 + Asio IO 线程 + 业务线程池；跨线程一律信号槽 QueuedConnection 投递回 UI；
- 媒体解码独立线程，渲染队列深度 2 丢帧保最新（05 §5）。

**Q41 本地缓存怎么做的？**
- SQLite：消息/会话缓存，(conv_id, seq) 参与 SQL 层去重；离线可看历史，登录增量同步（ADR-009）。

**Q42 为什么要分层解耦？（Android 预备）**
- net/协议/业务逻辑纯 C++ 不触 QWidget；UI 可替换；proto 平台无关——
  Android 端可选原生 Kotlin + protobuf 复用服务端全部协议（ADR + M8 评估文档）。

## 十、项目叙事（开放题）

**Q43 这个项目最难的地方是什么？**
- 建议答：消息可靠性模型在「弱网 + 多端 + AI 流式」三重条件下的收敛
  （推拉结合、seq 权威、占位消息、幂等补拉）——有设计、有自动化用例、有压测数据支撑。

**Q44 和真实 QQ 的差距在哪？（诚实+深度题）**
- 差距：海量账号体系、多端互踢策略完整度、E2EE、 Push 离线通道（APNs/厂商通道）、
  全球加速；但架构语义（接入/逻辑/存储分层、推拉结合、seq 模型）与工业 IM 同构。

**Q45 为什么做「酒馆」融合？（差异化亮点）**
- 把流行的 AI 角色扮演作为 IM 关系链上的一等公民：消息可靠性、漫游、社交传播（名片/广场）
  是独立酒馆工具没有的能力；同时给工程带来新命题：LLM 网关工程化、流式与可靠性协同、
  记忆一致性——这正是「IM + AI」的复合面试价值。
